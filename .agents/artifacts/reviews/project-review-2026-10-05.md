## Вывод

Проект пригоден для первого практического запуска: реализации адаптивного веб-интерфейса по Figma в подготовленном репозитории. Разделение этапов осмысленно, skills оформлены корректно, требования к адаптивности и визуальному подтверждению помогают избежать распространённых ошибок.

Это набор инструкций для агента, а не самостоятельно исполняемый оркестратор. Он задаёт процесс, но не подключает Figma, не устанавливает браузерные инструменты и не предоставляет приложение. README прямо сообщает об этих внешних зависимостях. Отсутствие собственного runtime, скриптов или отдельного файла конфигурации skill само по себе не является недостатком.

Для разработки полноценного приложения нужно дополнительно определить функциональные требования и интеграции. Это расширение области применения, а не причина переписывать четыре существующих skill. Фактическая эффективность harness пока не подтверждена сохранённым сквозным прогоном в этом репозитории.

## Замечания к процессу

### R1 · P2 · Матрица не гарантирует проверку границ поддерживаемого диапазона

Источник: [visual-validation.md:10](/Users/aialprokopev/Projects/design-implementation-harness/.agents/workflows/visual-validation.md:10), [responsive-contract.md:24](/Users/aialprokopev/Projects/design-implementation-harness/.agents/templates/responsive-contract.md:24).

Матрица требует референсные размеры, пять фиксированных ширин и `breakpoint −1/+1`. При этом контракт отдельно задаёт поддерживаемый диапазон, но его минимальная и максимальная ширины не входят в обязательные проверки. Например, для диапазона 320–1440 и мобильного референса 390 экран может получить `pass`, ни разу не проверившись на 320.

Также не требуется сама ширина breakpoint. При сочетании `max-width: 768px` и `min-width: 768px` оба правила действуют на 768; проверки 767 и 769 эту коллизию не обнаружат. Если 768 не совпадает с другим размером матрицы, дефект останется незамеченным.

Исправление: включить конечные границы поддерживаемого диапазона и `b−1, b, b+1` для каждого перехода. Отдельно определить, какие проверки нужны, когда фиксированный размер находится вне поддерживаемого диапазона. Согласованно обновить rule, workflow и template.

### R2 · P2 · Бюджет раундов не учитывает обязательную проверку интеграции

Источник: [visual-validation.md:14](/Users/aialprokopev/Projects/design-implementation-harness/.agents/workflows/visual-validation.md:14), [AGENTS.md:25](/Users/aialprokopev/Projects/design-implementation-harness/AGENTS.md:25).

Работник может использовать все три раунда и передать готовый экран. После этого координатор интегрирует изменение общего компонента или стилей. Повторная проверка затронутого экрана обязательна, прежние захваты уже недостаточны, а интеграция не восстанавливает бюджет. Четвёртый раунд допускается только для уже диагностированной локальной проблемы; обычная проверка регрессий этому условию не соответствует.

Процесс позволяет честно остановиться с `incomplete`, но способен вынужденно остановить и штатную интеграцию без установленного дефекта. Нужно заранее распределять общий бюджет: например, при параллельной работе резервировать последний раунд для интеграции, а общие зависимости по возможности стабилизировать до локального review. Определить, считается ли проверка после интеграции отдельным раундом. Лимит увеличивать необязательно.

### R3 · P2 · Смешанные доказательства не привязаны к состоянию кода каждого раунда

Источник: [visual-review.md:3](/Users/aialprokopev/Projects/design-implementation-harness/.agents/templates/visual-review.md:3), [visual-review.md:12](/Users/aialprokopev/Projects/design-implementation-harness/.agents/templates/visual-review.md:12), [visual-validation.md:19](/Users/aialprokopev/Projects/design-implementation-harness/.agents/workflows/visual-validation.md:19).

Workflow разрешает сохранять прежние захваты для незатронутых проверок. Однако шаблон содержит одну общую revision/working-tree state для отчёта; строки доказательств не фиксируют состояние кода или пакета на момент захвата. После нескольких незакоммиченных исправлений HEAD может оставаться тем же, а пометка `dirty` не позволяет восстановить, к какому варианту реализации относится конкретный screenshot.

Это ослабляет проверяемость решения «старое доказательство остаётся валидным», особенно после интеграции. Достаточно короткой записи для каждого раунда: commit плюс идентификатор/сохранённый diff рабочего дерева, версия пакета и затронутые файлы. Отдельная система версионирования не требуется.

## Готовность к написанию кода

| Сценарий | Оценка |
| --- | --- |
| Один адаптивный экран в существующем веб-приложении | Можно начинать после заполнения контекста и подготовки пакета |
| Несколько экранов с общими компонентами | Подход пригоден; заранее назначить владельцев и распределить раунды интеграции |
| Новый frontend-проект | Возможно, если стек, архитектура и scope определены; встроенного starter нет, и это явно указано |
| Интерфейс с API, авторизацией и изменением данных | Нужны дополнительные функциональные требования и проверки |
| Универсальная разработка backend, CLI или native-приложений | Текущие правила рассчитаны на адаптивный веб-интерфейс по Figma |

Поведение уже упомянуто в screen-spec, Responsive Contract и visual validation. Поэтому утверждать, что функциональная проверка совсем отсутствует, было бы неверно. Пробел в том, что её достаточность почти полностью зависит от заполнения свободного поля `Content/fixture, interactions, and component states`.

Для прикладного экрана стоит явно фиксировать применимые сведения: действие пользователя, ожидаемый результат, источник данных, запись/чтение, переходы, ошибки, загрузку, пустое состояние, права доступа и проверку результата. Для статической страницы эти пункты могут быть неприменимы. В readiness нужно учитывать отсутствие блокирующих вопросов о требуемом поведении, а не только дизайн-пробелов. В частности, отправку формы невозможно вывести из одного изображения Figma; такой вопрос должен идти к требованиям продукта/API, а не бесконечно возвращаться extractor.

## Что уже помогает решать задачу

1. Анализ существующего кода до реализации снижает вероятность дублирования компонентов и нарушения архитектуры.
2. Раздельные индекс и пакет уменьшают повторное чтение Figma и позволяют передавать конкретные входные данные работнику.
3. Одна задача на все размеры и отдельный контракт предотвращают создание трёх несвязанных версий экрана.
4. Явное разделение наблюдений и предположений делает неполный дизайн пригодным для обсуждаемой реализации.
5. Владелец общей инфраструктуры снижает риск конкурирующих правок при делегировании.
6. Обязательные захваты и статус `incomplete` препятствуют объявлению визуально непроверенной работы завершённой.

Это ожидаемые преимущества устройства процесса. Насколько они экономят время, вызовы инструментов и исправления именно в вашей среде, нужно измерить на реальном запуске.

## Минимальные следующие шаги

1. Исправить R1–R3 и короткие неоднозначные формулировки; расширять количество skills пока не требуется.
2. Перед пилотом проверить доступность Figma, запуска приложения и захвата Playwright. Инструменты уже учитываются в контексте; добавить раннюю фактическую проверку их возможностей.
3. Подготовить один реальный экран с desktop/mobile и вывести поведение между ними в контракте. Выбрать экран с одним взаимодействием и общим компонентом.
4. Провести полный цикл и сохранить пакет, код и review. Проверить также один recovery-запрос и обновление общего компонента. Это предложенный пилот, в текущем ревью он не выполнялся.
5. По результатам пилота добавлять только инструкции, необходимость которых проявилась на практике. Для полноценного приложения дополнить существующую спецификацию функциональными требованиями.

Начать писать код с агентом уже можно. Наиболее полезный следующий этап после небольших исправлений — практический прогон, который покажет, где реальному агенту не хватает данных или координации.
